L'API Shortext permet à vos systèmes d'envoyer des messages, de suivre les conversations, de gérer agents et canaux, de recevoir des webhooks et de connecter les canaux de vos propres clients. C'est une API JSON sur HTTPS.

## URL de base

| Version | URL de base | Statut |
| --- | --- | --- |
| **v2.0** | `https://shortext.ny-corp.io/api/v2.0` | Actuelle, à utiliser pour toute nouvelle intégration |
| v1.0 | `https://shortext.ny-corp.io/api` | Historique, voir [v1.0](/fr/api-reference/v1.0/introduction) |

Envoyez `Accept: application/json` et, avec un corps, `Content-Type: application/json`. Authentifiez chaque requête avec une [clé API](/fr/api-reference/authentication).

## Enveloppe de réponse

Toutes les réponses ont le statut HTTP **200**, que la requête ait réussi ou non. Il y a deux exceptions : une requête au-delà de la [limite de débit](#limites-de-débit) (HTTP 429) et une version d'API retirée (HTTP 410, voir [Versionnement](/fr/api-reference/versioning)). Le résultat est toujours dans le corps :

```json Succès
{
  "success": true,
  "message": "Request success.",
  "code": 1000,
  "body": { "id": "AGI-XXXXX", "name": "Support" }
}
```

```json Échec
{
  "success": false,
  "message": "Missing the permissions.manage_integrations permission",
  "code": 1005,
  "body": null,
  "trace_id": "6f1c2e..."
}
```

| Champ | Description |
| --- | --- |
| `success` | `true` quand la requête a réussi. Vérifiez-le en premier. |
| `code` | `1000` en cas de succès, sinon un [code d'erreur](/fr/api-reference/errors). |
| `message` | Une description lisible. Ne l'analysez pas. |
| `body` | Le résultat : un objet, une liste, une liste paginée ou `null`. En cas d'erreur de validation, les erreurs par champ. |
| `trace_id` | En cas d'échec uniquement : transmettez-le au support pour retrouver votre requête. |

<Warning>Ne vous fiez pas au statut HTTP pour détecter les erreurs : lisez toujours `success` et `code`.</Warning>

## Pagination

Les listes sont paginées, 50 éléments par page, les plus récents d'abord sauf mention contraire. Demandez une page avec `?page=2`. Le `body` d'une réponse paginée est :

```json
{
  "current_page": 1,
  "data": [ { "id": "AGI-XXXXX", "name": "Support" } ],
  "first_page_url": "https://shortext.ny-corp.io/api/v2.0/agents?page=1",
  "from": 1,
  "last_page": 3,
  "last_page_url": "https://shortext.ny-corp.io/api/v2.0/agents?page=3",
  "next_page_url": "https://shortext.ny-corp.io/api/v2.0/agents?page=2",
  "path": "https://shortext.ny-corp.io/api/v2.0/agents",
  "per_page": 50,
  "prev_page_url": null,
  "to": 50,
  "total": 128
}
```

Suivez `next_page_url` jusqu'à ce qu'il vaille `null`.

## Dates et identifiants

- Les dates sont des chaînes ISO 8601, par exemple `2026-10-24T09:12:44+00:00`.
- Les identifiants sont des chaînes opaques (`AGI-XXXXX`, `ste_...`, uuid). Stockez-les comme des chaînes, ne les analysez jamais.

## Limites de débit

| Appelant | Limite |
| --- | --- |
| Requêtes authentifiées | **300 requêtes par minute et par entreprise**, partagées par toutes ses clés API et par la v1.0 et la v2.0 |
| Routes publiques (par exemple `GET /api/versions`) | 60 requêtes par minute et par adresse IP |

Chaque réponse indique où vous en êtes :

| En-tête | Signification |
| --- | --- |
| `X-RateLimit-Limit` | Le nombre de requêtes autorisées par minute. |
| `X-RateLimit-Remaining` | Les requêtes restantes dans la minute en cours. |

Au-delà de la limite, l'API répond avec le statut HTTP **429**, un en-tête `Retry-After` (en secondes) et l'enveloppe habituelle :

```json
{
  "success": false,
  "message": "Too many requests: retry in 42 seconds",
  "code": 1001,
  "body": null,
  "trace_id": "..."
}
```

Attendez `Retry-After` secondes avant d'envoyer d'autres requêtes. Étalez les traitements par lots dans le temps, et utilisez les [webhooks](/fr/api-reference/webhooks) plutôt que d'interroger l'API en boucle.

## Contenu de l'API

| Ressource | Ce que vous pouvez faire |
| --- | --- |
| Compte | `GET /me` : l'entreprise et la clé derrière votre jeton |
| Agents | Créer, modifier, supprimer et restaurer des agents |
| Canaux | Lister les canaux, les rattacher à des agents ; créer et gérer des endpoints Shortext |
| Conversations | Lister, lire, démarrer, répondre, prendre en main, rendre la main, assigner |
| Modèles | Lister, créer et modifier les modèles WhatsApp |
| Webhooks | Gérer les endpoints, les tester, lire et relancer les livraisons |
| Sessions hébergées | Laisser vos clients connecter leur numéro WhatsApp ou leur boîte mail sur une page Shortext |
| Tickets | Ouvrir, modifier, commenter et répondre aux tickets ; gérer les statuts et les politiques de SLA de chaque agent |
| Connaissances | Alimenter la base de connaissances d'un agent (Markdown ou PDF) et ce qu'il sait des contacts |
| Liens dynamiques | Créer des liens courts qui ouvrent votre application, enregistrer les applications, lire les clics |
| Facturation | Lire le solde et les mouvements du portefeuille de l'entreprise |

La liste complète se trouve dans **Endpoints**, générée à partir de la spécification OpenAPI.
